# 016 — Server-Authoritative Client Balance (`coins` field)

## Status

Accepted

## Context

The client's displayed coin balance is currently a **client-side running
total**:

- `auth_result` is the only server→client packet that includes `coins`
  (`ANCHOR_PROTOCOL.md` § Authentication).
- After login, the client adjusts balance locally in `onGameOver()` via
  `coins - paid + received` arithmetic on `game_over.statistics` entries.
- `persistUser()` (localStorage) was only called from `onAuthResult()` until
  FIX-18 (2026-08-02), so even correct in-memory updates were lost on
  refresh.

Server-side economy (`GameFinishService::finishGame()`, kick/ban refunds,
`handleNoSurvivors()`, apartment payments, daily bonus) is verified correct
against `game.db`. The desync is architectural: the client has no
authoritative re-sync path outside login.

**Concrete failure modes (client-only or arithmetic-dependent):**

| Path | Server updates DB? | Client updates display? | Survives refresh? |
|------|-------------------|-------------------------|-------------------|
| Victory / last_survivor payout | Yes | `onGameOver()` arithmetic | FIX-18: yes (persist) |
| no_survivors refund | Yes | `onGameOver()` arithmetic | FIX-18: yes (persist) |
| Admin kick/ban refund (in-game) | Yes | **No handler** | No |
| admin_close_room refund | Yes | **No handler** | No |
| Apartment payment (agree) | Yes | **No handler** | No |
| Daily bonus on reconnect | Yes (login path) | Only if fresh `auth_result` | N/A at login |
| Dropped `game_over` packet | Yes | Stale | No |

FIX-18 closes the refresh symptom for `game_over` paths but does not fix
arithmetic trust or uncovered paths. A protocol-level authoritative
`coins` field is the durable fix.

Per `ANCHOR_PROTOCOL.md` Protocol Compatibility Rule, adding optional
fields is additive (no version bump). Per `ANCHOR_RULES.md` Rule 7, this
economy-adjacent client-facing change requires ADR approval before
implementation.

## Decision

### 1. Extend `game_over.statistics[]` entries (primary)

Add optional `coins` (int) per statistics row — the player's **actual
post-transaction balance** read from `users.coins` in the database **after
the payout/refund PDO transaction commits**, not recomputed from
`paid`/`received` deltas.

```json
{
  "type": "game_over",
  "winner": "alice",
  "reason": "victory",
  "prize": 120,
  "final_bank": 120,
  "statistics": [
    {"username": "alice", "paid": 10, "received": 120, "coins": 610},
    {"username": "bob",   "paid": 10, "received": 0,   "coins": 490}
  ]
}
```

**Server implementation site (future Epic):** `GameFinishService::finishGame()`
and `handleNoSurvivors()` — after `commit()`, re-read each affected
`user_id` via existing `user_by_id` prepared statement and attach `coins`
to the matching statistics entry. No change to payout math or transaction
boundaries.

**Client (future Epic):** `onGameOver()` sets
`state.user.coins = me.coins` when present (fallback to arithmetic for
backward compatibility), then `persistUser(state.user)`.

### 2. Extend `reconnect_state` (secondary, recommended)

Add top-level `coins` (int) for the reconnecting player on all
`reconnect_state` branches (`waiting`, `playing`, `apartment`).

```json
{"type": "reconnect_state", "status": "playing", "coins": 490, ...}
```

**Server:** `ReconnectService::buildReconnectState()` — read once from DB
for `$player['user_id']` before send.

**Client:** `onReconnectState()` — if `pkt.coins != null`, set
`state.user.coins = pkt.coins` and `persistUser(state.user)`.

Covers mid-game disconnect/reconnect without requiring a finished game.

### 3. Refund notification paths (tertiary, evaluate at implementation)

Paths that mutate `users.coins` without `game_over`:

| Event | Suggested approach |
|-------|-------------------|
| Admin kick/ban refund | Add `coins` to existing `player_left` packet **or** new lightweight `balance_updated` packet |
| admin_close_room | Include `coins` in `game_over` (no_survivors/admin_close already uses finish path) — verify coverage |
| Apartment agree payment | Add `coins` to post-payment broadcast or per-player ack |

**Preference:** avoid a new packet type if an existing per-player packet
already fires at the mutation site. If no packet exists, add
`balance_updated`:

```json
{"type": "balance_updated", "coins": 495}
```

Server → single connection, sent immediately after any DB balance commit
outside `game_over` / `auth_result`.

### 4. Client discipline (future Epic)

Whenever `state.user.coins` changes from a server field:

1. Prefer server `coins` over local arithmetic.
2. Call `persistUser(state.user)`.
3. Call `UI().updateLobbyUser(state.user)`.

Deprecate client-side `paid/received` arithmetic once server fields are
deployed and tested (keep fallback one release).

## Explicit non-goals

- No change to payout/refund **calculation** or transaction logic in
  `GameFinishService`, `GameService`, `AdminService`, or
  `PreparedStatements`.
- No new economy rules.
- FIX-18 (persist after `game_over` arithmetic) remains valid as interim
  mitigation until this ADR is implemented.

## Consequences

**Positive:**

- Client display matches `game.db` after every covered path, including
  refresh/reconnect.
- Eliminates silent desync from dropped packets, missed handlers, or
  stale localStorage.
- Additive protocol — old clients ignore new fields.

**Negative:**

- Extra DB read(s) after commit in finish/refund paths (acceptable on
  game-end / infrequent admin events).
- Multiple touch points (finish, reconnect, admin, apartment) — needs a
  single implementation Epic with a verification matrix.
- `balance_updated` (if chosen) adds one packet type to registry.

Clients without `coins` field continue current arithmetic + FIX-18 persist.
