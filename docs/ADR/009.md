# 009 — `host_changed` Packet for Lobby Host Transfer Notification

## Status

Accepted

## Context

`LobbyService::transferHost()` (`src/Lobby/LobbyService.php`) correctly
updates `$room['host_conn_id']` in server memory when the lobby-AFK timer
detects an inactive host (>= `LOBBY_HOST_TIMEOUT` seconds, per
`ANCHOR_CORE.md` § Lobby AFK Timer) and logs the change — but sends **no
packet** to any client. Neither the outgoing host, the new host, nor any
other player in the room is notified.

`ANCHOR_PROTOCOL.md` currently has no packet type for host-change
notification. `host` appears only inside `room_joined`, sent once at
initial join time.

Live-reproduced symptom: after the 120s threshold passes, the server-side
host does change, but the "Начать игру" (Start Game) button never appears
for the new host and never disappears for the old host — the client has
no signal to react to.

Per `ANCHOR_PROTOCOL.md` Protocol Compatibility Rule ("New packets may be
added"), this is additive and does not require a version bump. This
project's convention (ADR-003 through ADR-007) documents every protocol
addition as a lightweight ADR for traceability.

## Decision

1. **New packet, Server → Room:**
   ```json
   {"type": "host_changed", "host": "username"}
   ```
   Broadcast to every active player currently in the room (same `foreach`
   + `sendJson` pattern as `player_left` / `player_joined` in
   `LobbyService`), whenever `host_conn_id` changes inside
   `transferHost()`.

2. **Implementation site:** `LobbyService::transferHost()`, immediately
   after `$room['host_conn_id'] = $connId` and `$newHostUsername` are
   set. Primary trigger for this task: lobby-AFK timer callback in
   `startLobbyAfkTimer()` (waiting-room host timeout). The broadcast lives
   in `transferHost()` itself so any caller that successfully transfers
   host also notifies clients; no separate per-call-site logic.

3. **Registry update:** add `host_changed` to `ANCHOR_CORE.md` § Protocol
   Packet Types and document the JSON shape in `ANCHOR_PROTOCOL.md` §
   Lobby. No existing packet renamed, removed, or changed in meaning. No
   Room/Player Structure change (`host_conn_id` already exists).

4. **Client:** `public/js/app.js` handler updates `state.room.host` and
   re-renders the room panel so Start Game button visibility recalculates.

## Explicitly out of scope

`ApartmentService` / `AdminService` host transfer during kick/ban in the
`apartment` phase is a **separate, already-documented KNOWN GAP**
(`IMPLEMENTATION_STATUS.md`, EPIC-9.3 note:
`removePlayerFromApartment()` does not perform host transfer when the
host is kicked/banned in apartment state). That gap is about **missing
transfer logic entirely**, not a missing notification for a transfer that
already happens. Do not fix or touch that path in this task; it needs its
own future Epic once the transfer logic itself exists there.

## Consequences

Positive:
- Clients learn immediately when lobby host changes (AFK timeout, or host
  leave triggering `transferHost()`), without page refresh.
- Start Game button visibility stays in sync with server-side
  `host_conn_id`.

Negative:
- One new packet type for the Phase 12 client to handle (implemented in
  this task for `app.js`).
- `test_protocol_completeness.php` cross-reference count increases by one
  allowed packet (no warning expected).

## Compatibility

Additive only. No packet, field, or action renamed/removed. No economy,
database schema, or timer threshold changes.

- `ANCHOR_PROTOCOL.md` § Lobby: new `host_changed` packet section.
